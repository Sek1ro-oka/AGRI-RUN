# 智慧浙农林 2.51「农林快跑」：里程不累计的代码分析与分步改进方案

日期：2026-10-28（Asia/Hong_Kong）。本文可直接交给本项目开发者执行。

## 1. 先说明实际结论

**已在你提供的 APK 中找到“轨迹在增加，但里程不增加”的具体代码分支。它不是只根据位置点画线就累加距离，而是另有速度、精度、点间距及 `userIsRunning` 条件；其中 `userIsRunning` 受到陀螺仪检测控制。**

因此，不能再把问题简单归为“模拟位置都被拒绝”，也不能承诺加几个 Location 字段就一定解决。正确推进方式是：补高德定位 SDK 接收端取证、与 GoGoGo 做同条件对照、修本项目输出链路中实际存在的差异，并将接收兼容与目标运动判定分别验收。

本文提供的是有代码依据、可以实施和验证的步骤。**尚无真机动态证据证明本次失败具体落在哪个条件，也没有证据支持“照抄 GoGoGo 的公开定位服务即可让手机静止时一直累加农林快跑里程”。** 目标 App 的独立运动判断不是发送端的公里数参数。

## 3. APK 中具体找到了什么

### 3.1 真正负责里程的类

`edu.zafu.uniteapp.gd.LzBgLocHelper`：

- `startLocation()`：创建高德 `AMapLocationClient` 并配置运动定位。
- `handleLocation(AMapLocation)`：处理位置、向轨迹列表加点、选择是否增加 `totalMeter`。
- `registerSensor()`：按配置注册传感器。
- `handleSensorAcc()`：更新是否正在运动的内部状态。
- `timerAction()`：计时并调用传感器状态检查。

`edu.zafu.uniteapp.sport.SportActivity` 使用上述 helper 管理运动、画线和显示结果。地图的“我的位置”显示也有自己的设置，不能把蓝点移动直接等同于里程分支通过。

### 3.2 接收端是高德定位 SDK，不是 Google FLP

`startLocation()` 可见：高精度模式、GPS 优先、持续定位、传感器开启以及 `AMapLocationPurpose.Sport`。定位间隔从 `LgBasicData.getSportGpsInterval()` 读取后乘 1000 转毫秒。

这意味着我们自己的 GPS、network、framework fused、GMS FLP 四通道通过后，**仍缺少“高德定位 SDK 实际交给该运动模块什么”的证据**。不能继续把 GMS 探针通过当作完整接收兼容性。

另一个已确认项：代码显式调用 `setMockEnable(false)`；随后调用的 Sport 场景，在 APK 自带 SDK 的实现中也把 `isMockEnable()` 对应的字段设为 false。这里不仅检查了方法调用名，也核对了该 SDK 的场景处理及字段读写，避免忽略配置覆盖顺序。

这表明目标接收端没有声明接受模拟 GPS。它会如何表现，仍需要看实际高德回调的 errorCode、errorInfo、locationType 和坐标，不能只凭静态配置就断言界面完全不会移动。

### 3.3 轨迹点和公里数分开处理

以下是根据 `handleLocation()` 重述的**运行态主要分支**，不是目标源码原文，也没有包含暂停态、首点、报错处理等全部细节：

```text
位置回调成功，且不是空坐标
  ↓
进入目标的 running 状态处理
  ↓
精度合格，SDK 速度处于运行配置允许范围
  ↓
第一点：加入轨迹，尚不能累计两点距离
后续点：计算与最后一个已接纳点的地理距离 deltaMeters
  ↓
若 deltaMeters > 0
且 deltaMeters 小于该分支读取的上限
且 userIsRunning == true
  → totalMeter += deltaMeters
  ↓
即使上面的里程条件不成立，仍可把这个点加入轨迹列表
```

**最后两步就是“有线但没公里数”可以成立的代码依据。** 速度、精度不合格时还可能走另外的显示/位置上传路径，故需要区分蓝点、轨迹线、实时里程及最终保存结果。

### 3.4 一个值得特别验证的距离条件

在该 APK 的 `handleLocation()` 中，点间地理距离计算结果直接与 `getSportSpeedMax()` 返回值比较，再决定是否累计。这个局部分支没有先除以两个位置点的时间差。

因此，不能简单理解成“速度在范围内就一定累计”。回调间隔变长时，点间距可能超出这个条件，轨迹仍增加而距离被跳过。

APK 的 `LgBasicData` 构造默认值包括定位间隔 1 秒、速度上限数值 10、速度下限 0.1、精度上限 50。**这些只是构造默认值，不是已确认的登录后运行配置，不能硬编码成兼容参数或服务端当前规则。**

用默认值做纯数学例子：35 km/h 约 9.72 m/s；若接收回调之间相隔 2 秒，相邻点可能约 19.44 米。速度本身可能还在上限内，但点间距已经超过数值 10。40 km/h 又约 11.11 m/s，可能直接超出速度条件。

所以此前 `docs/12_目标App里程不累计_排查与修改.md` 建议“2000 ms + 30–40 km/h”不能继续作为本目标的默认解决办法，反而可能恶化问题。

### 3.5 `userIsRunning` 来自陀螺仪判断

`registerSensor()` 在运动检测配置开启时调用 `SensorManager.getDefaultSensor(4)`。Android 中 4 是 **TYPE_GYROSCOPE（陀螺仪）**，不是计步器，也不是加速度计。字段/函数名中的 `SensorAcc` 不能改变实际注册的传感器类型。[Android Sensor 常量](https://developer.android.com/reference/android/hardware/Sensor#TYPE_GYROSCOPE)。

`handleSensorAcc()` 在配置开启、传感器存在、状态为 running 等条件下，周期性检查运动样本；不满足时可将 `userIsRunning` 设为 false，并有“请跑起来”等提示。`handleLocation()` 的里程增加分支直接读取这个布尔值。

因此：**若本次停计确实由这个分支造成，单纯调整 GPS 坐标、速度、accuracy、satellites 或 GMS 输出，不能直接改变另一个进程里的运动状态。** 本项目的标准位置接口并不注入陀螺仪数据。

这里确认的是“代码存在这种控制关系”。当前账号是否开启检测、设备传感器是否存在、现场何时变 false，尚未动态确认。不能据此保证用户所有失败都来自陀螺仪。

## 4. 对照 GoGoGo：应参考哪些方法

本次通过 GitHub CLI 重新读取了固定提交的公开 `ServiceGo.java`：

| 项目 | GoGoGo 公开实现 | 本项目现状/行动 |
| --- | --- | --- |
| 系统接口 | LocationManager 测试 provider | 同类接口已具备，保留 |
| 输出来源 | GPS 与 network | 当前还尝试 framework fused / 可选 GMS；需要可单独选择来源做对照 |
| 发布节奏 | 循环内约 100 ms 等待 | 当前常用 500 ms，并有发送间隔选项；增加有测量结果的参考档位 |
| 速度和航向 | 在 Location 中设置 | 已具备；以独立接收结果验证，不重复宣称缺失 |
| 时间戳 | wall time + elapsed realtime | 已具备；检查单调性及发送/接收对齐 |
| GPS 精度字段 | 使用 Criteria.ACCURACY_FINE 数值填入 setAccuracy | 当前移动 3 米；将差异作为实验变量，不把常量名称误当精度测量 |
| 卫星 extras | GPS 的 satellites 字段 | 当前填充器已有模拟字段；不等于真实 GNSS 状态或目标陀螺仪状态 |
| 目标 App 里程/传感器 | 该公开服务未直接写目标状态 | 不能假设它有一个公开的“给农林快跑加公里”接口 |

用户报告 GoGoGo 有效是重要实验线索，应认真复现。还需要记录实际使用的 GoGoGo/VirtGO APK 版本、同一目标版本、同一手机、后台状态、账号运行配置和使用情形。公开仓库的某个源码版本不必与用户实际 APK 完全相同。

不得把“用户观察有效”改写成“用户不可能有效”；也不得把它当作已经证明公开代码绕过了所有上述条件。

### 第三步：增加 GoGoGo 公开参考发布模式

负责人：开发者。预计修改：`SimulationService`、输出后端配置、`AndroidMockProviderApi`、诊断记录。

1. 增加显式测试配置 `GOGOGO_REFERENCE`，来源限定 GPS + network，先隔离 platform fused/GMS 的影响；保留普通配置，不删除现有通道。
2. 增加 100 ms 参考发布档位，并记录实际调度间隔。可以使用现有 RunConfig 的下限；先核对当前调用链，避免只改 UI 选项而服务仍按 500 ms 发。

4. 逐项比较 GoGoGo 的 provider 属性、Location 基础字段及接收结果。当前代码已经按 GPS/network 区分属性，不应再把它说成尚未实现。
5. 若要测试 accuracy 差异，使用明确标注的模拟参数，对比一次只变一个因素；不加入随机抖动，不宣称模拟卫星 extras 能改变目标的真实陀螺仪数据。
6. 只有独立高德 reader 或目标观察显示改善，才将某个参考参数作为可用配置。不要把 100 ms 本身当作必定成功的答案。

该步骤能修的是位置发布和接收的兼容性；它不能直接写目标 `userIsRunning`、`totalMeter` 或接收端的 mock 策略。

### 第四步：同机对照，逐层定位失败点

负责人：开发者与用户配合。预计产物：两轮相同条件的对照表。

1. 先做真实正常定位的短时基线，确认目标自身能够进入记录状态。
2. 选择同一路线、相同坐标系、相同速度和时段，分别运行 GoGoGo、本项目普通模式、本项目参考模式；每轮停止清理后再切换。
3. 在目标页面记录“蓝点”“轨迹线”“实时距离”“提示文字”和发生时间；不能只截主项目公里数。
4. 探针同时记录高德 reader 与 framework 的原始回调；字段日志脱敏后保存。
5. 若位置侧相同而运动状态不同，再核对目标实际配置及真实传感器接收状态。在自己的诊断工具里只读观察传感器可用性和真实采样，不向目标注入或伪造传感器事件。
6. 对无法观测的目标内部变量标记未知。没有内部状态证据时，只能说“与运动状态门控相符”，不能声称现场已经证实。

| 结果 | 具体行动 |
| --- | --- |
| 高德 reader 无位置/报错 | 根据 SDK 错误与配置修发布或接收链路，不继续堆卫星字段 |

### 第五步：增加本项目自己的接收契约回归

负责人：开发者。预计产物：纯逻辑测试 + Android 集成测试。

在我们自己的测试模块中建一个简化的 `DistanceDecision`，输入位置质量、速度、点间距和运动状态，输出“是否入轨迹”“是否计距”“原因”。该模块仅用于复现本次发现的语义，不能冒充目标的完整实现或最终服务器判断。

必须覆盖：

- 位置与速度都有效、运动状态允许时，合理增量正常累计。
- 同样的有效轨迹点，运动状态不允许时，轨迹可以增加而里程为 0。
- 回调间隔变长导致点间距过大时，明确说明拒计原因。
- 单位一致：界面 km/h、Location.speed 为 m/s、地理距离为米；比较条件不能混成“accuracy 大于步长必然拒计”。
- 100/500/1000 ms 发布档位不改变路线随时间的理论位置；后台延迟有日志和状态处理。
- 高德/GMS/framework 各来源的成功、失败、不可用分别记录。

不要通过把所有轨迹点无条件相加来冒充“目标里程已修好”。本项目自己的距离展示与第三方接受的距离是两份不同的状态。
