## 4. 需要交给写手修复的确定问题

### R32-01〔P1〕运行中路线转单点会触发非法状态转移

位置：`app/src/main/java/org/localroute/app/service/SimulationService.java:368`，特别是第 392 行；`route-core/src/main/java/org/localroute/core/LoopStateMachine.java`。

`switchRouteTaskToSinglePoint()` 完成字段切换和首帧发送后，无条件执行 `stateMachine.providerReady()`。这个方法尝试转到 RUNNING，而状态机没有允许 RUNNING→RUNNING。

最小复现直接调用当前工程编译的状态机类：

```java
machine.markReady();
machine.startRun();
machine.providerReady(); // 此时 RUNNING
machine.providerReady(); // 抛 IllegalRunStateException: RUNNING -> RUNNING
```

实际服务由 `runGuarded()` 捕获该异常后进入失败清理。因此可能出现先传送一帧、随后停止保持的行为。暂停态转 RUNNING 则允许，不能把暂停态、单点态成功等同于这个运行态分支已经覆盖。

用户此前反馈的测试成功继续有效；本问题针对源码中这个明确的 RUNNING 分支，不能以部分场景成功关闭它。

**修改要求：**

1. 在变更任务字段前验证原状态。
2. 原状态 RUNNING：保持 RUNNING，不调用 providerReady。
3. 原状态 PAUSED：明确产品行为；若传送后恢复保持，则使用对应的恢复状态操作并同步时钟。
4. 原状态 STARTING：专门处理启动与传送命令顺序；不能盲目复用运行态代码。
5. 不要为了躲这个错误，在全局状态机中随意增加 RUNNING 自转移；先修调用语义。

**必补测试：**运行路线转单点、暂停路线转单点、首次提交失败、转换后继续保持多个 tick、旧路线不会重新发布。

### R32-02〔P1〕高德开发对照实际上也关闭了 mock

位置：`location-probe/src/main/java/org/localroute/probe/AmapReader.java:120`，第 130–131 行。

当前顺序：

```java
option.setMockEnable(mockEnable);
option.setLocationPurpose(AMapLocationPurpose.Sport);
```

Sport 场景会覆盖此前设置。使用当前依赖的 **高德定位 SDK 6.4.5 实际 JAR** 在本机直接构造同样选项，得到：

```text
primary.mock=false
dev.mock=false
primary.timeout=5000
dev.timeout=5000
dev.mock.after.override=true
```

因此当前 `amap-sdk` 与 `amap-sdk-dev` 不是有效的 false/true 对照。用户报告只打印 primary 的 getter，启动文字却声称 dev=true，这会误导判断。

**修改要求：**

- 主通道按目标真实调用顺序构造，保留最终 getter 的实际值。
- 开发对照先完成同样的 Sport 预设，再最后 `setMockEnable(true)`；只修改探针自己的开发对照客户端。
- 两条通道分别打印最终 getter。增加断言：primary=false、dev=true；其他要对照的选项相同。
- 将“Sport 必须最后调用”的注释改为“场景会覆盖选项，主策略与显式对照按各自目的安排顺序”。
- 修复并不需要有效 Key 或真机：选项构造、getter 和单元测试可以先完成；实际 SDK 接收差异随后现场验证。
- 不要根据现有两条通道的相同结果推导“允许和拒绝 mock 完全没有区别”。

### R32-03〔P1〕每次传送可能增加一个长期 tick 循环

位置：`SimulationService.handleTeleport()`、`switchRouteTaskToSinglePoint()`、`scheduleNextTick():605`。

运行中已经有一个待执行 tick。传送立即发帧后又调用 `scheduleNextTick()`；该方法直接 `postDelayed(tickRunnable, interval)`，没有移除旧待执行 tick，也没有“已有调度”守卫。两个回调执行后又各自排下一次，会形成多个发布循环。

这会使反复 A/B/C 操作后的发布节奏变密或成簇，与“时快时慢”有关。探针请求最小接收间隔时可能看不到全部紧邻帧，单次报告的约 500 ms 中位数不能排除发送端重复排队。

**修改要求：**在同一服务 Handler 上维持最多一个待执行 tick。可在统一排程入口先移除旧回调，再排下一次，或者维护可测试的 `tickScheduled` 状态。所有开始、暂停、传送、转换、停止路径共用这一规则。

**必补测试：**初始有一条 tick 时连续传送 20 次，待执行周期任务仍最多一条；运行一段时间后发布数不因传送次数倍增；停止后为 0。

### R32-04〔P1〕跨应用时悬浮条状态可能停止更新

位置：`app/src/main/java/org/localroute/app/ui/MainActivity.java:233`、`:277`。

悬浮条仍由 Activity 创建，状态更新依赖 `snapshot().observe(this, ...)`。Activity 停到后台后，这个生命周期观察者不再接收 LiveData 更新，但窗口仍可留在其他 App 上方。

可触发的场景：空闲时显示悬浮条→切到目标 App→点 A 启动单点。传送可能成功，但悬浮条仍显示旧的“未运行”，暂停/停止仍置灰。Activity 被销毁时又会直接 hide，不能把“窗口能在切 App 时暂留”解释为完整常驻控制。

**修改要求：**把悬浮会话状态订阅从 Activity 的 STARTED 生命周期中独立出来；由实际持有悬浮会话的控制器/服务负责主线程订阅与成对注销。运行态优先复用既有服务，空闲常显按 Android 允许的生命周期设计。不要仅加一个永不注销的 observeForever。

**必补测试：**Activity 已 STOPPED 时冷态传送，面板更新为单点运行且停止可点；服务停止后面板同步；重建 Activity 不产生两个窗口/订阅。

## 5. 其他应一并完成的修正

### R32-05〔P2〕探针报告区分“无速度”“速度 0”和“错误回调”

`ChannelStats.averageSpeedMps()` 在没有速度样本时也返回 0；`ProbeActivity.handleAmapFrame()` 将错误回调同样加入位置与距离统计。这样摘要可能把无速度字段当静止，把 SDK 错误或默认坐标当作有效轨迹。

要求：

- 分开记录 totalCallbacks、validFixes、errorCallbacks、speedSamples；无速度样本显示“未知/未提供”。
- 错误回调保留 errorCode/errorInfo，但不加入有效距离和速度统计。
- 传送与路线测试分开起统计会话。纯传送报告显示“位置跳变累计”，不显示为运动距离。
- 对 mock 标记只报告 SDK 观测值，不作真实性或绕过结论。
- GMS 增加最后回调年龄、完整起止时间，以及发送侧进入模式、提交成功/失败/丢帧/在途状态，才能分析本次只有 5 帧的原因。当前摘要不足以下结论。

### R32-06〔P2〕保存修复还缺“切换草稿”保护

`RouteEditorViewModel.markSavedIfUnchanged(revision)` 只比较 editRevision；`load()` 和 `newDraft()` 没有递增该值。

保存 A 的后台任务进行时，切到 B 或新草稿但尚未编辑，旧回调仍可能把当前草稿标记为已保存。这个窗口没有被“保存期间加点”的 revision 检查覆盖。

保存令牌至少含 `routeId + draftGeneration + editRevision`；加载、新建/替换草稿时更新 generation。补保存过程中加载 B、新建空草稿、删除后回调的测试。

### R32-07〔P2〕文档与日志仍有互相矛盾的状态

- `docs/12` 前表称 0.3.2 已新增 `GOGOGO_REFERENCE`，后表又写未做；源码检索未发现该模式，应统一为实际状态。
- `DistanceDecision` 是纯逻辑测试模块，其编写不依赖真机。参考发布模式的参数、调度与单位测试也可先开发；只有目标接收效果与同机对照需要设备。
- `PublishCadence` 测试不能替代 `SimulationService` 调度与状态转换测试。R32-01 和 R32-03 正是已有测试全绿仍漏掉的路径。
- 当前发布字段日志仍推荐“提高速度或拉长间隔”；针对本目标应改为记录观测和明确实验变量，避免与 `docs/13` 的已知条件相冲突。

现在目标已计距成功，参考发布模式与 DistanceDecision 可以作为后续诊断能力按优先级安排，不再作为本次成功必须补齐的条件；但不能把“选择暂缓”写成“没有真机所以无法编写”。
