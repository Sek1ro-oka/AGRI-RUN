## 0. 真机验收的结论先写清楚

用户在真机上确认：**目标 App 已经能记录模拟运动距离**。所以「目标 App 不累计里程」这条核心需求，
从 0.3.0 的「未实测」变成 0.3.3 的「用户真机反馈通过」。本文件后面所有内容都是**可用性缺陷**，
不是需求没实现。

同时纠正一条容易被误读的证据：探针那份「27 帧、595.1 米、均速 0.00 m/s」的报告是**点 A/B/C 传送**
场景的产物——位置跳变的累计不是跑步里程，均速为 0 是正常的。纯传送测试必须与路线测试分开统计
（见 R32-05）。

## 1. R32-01 路线运行中传送把自己打断（P1）

**现象**：路线跑着，在悬浮条点 A/B/C，目标 App 只跳到新位置一下就停住。

**根因**：`SimulationService.switchRouteTaskToSinglePoint()` 无条件调 `stateMachine.providerReady()`，
而 `providerReady()` 固定执行 `transitionTo(RUNNING)`；`LoopStateMachine` 的允许表里没有
`RUNNING → RUNNING` 这条边，于是抛 `IllegalRunStateException`，被 `runGuarded()` 当成致命错误，
走失败清理。

**修法**：把「切模式时状态该怎么动」抽成 `route-core/src/main/java/org/localroute/core/TaskModeSwitch.java`
的纯函数，服务只照着做：

| 原状态 | 状态动作 | 时钟动作 | 发布的状态 |
| --- | --- | --- | --- |
| `RUNNING` | `KEEP_RUNNING`（**不调** `providerReady`） | `RESTART`（新起点的计时重新开始） | RUNNING |
| `PAUSED` | `KEEP_PAUSED`（传送不自动恢复） | `KEEP_PAUSED`（不重置已累计的有效用时） | PAUSED |
| `STARTING` | `PROMOTE_TO_RUNNING`（唯一允许调 `providerReady` 的情形） | `RESTART` | RUNNING |
| 其它 / 空 | `UNSUPPORTED`（只记诊断，不抛异常） | — | 原状态 |

没有给状态机加 `RUNNING → RUNNING` 自转移——那会把「非法边」这个安全网拆掉。

**测试**：`route-core/src/test/java/org/localroute/core/TaskModeSwitchTest.java` 5 例，
覆盖「RUNNING 不调 providerReady」「PAUSED 不自动恢复」「STARTING 推进」「终态 UNSUPPORTED」「describe」。

**没验**：真机上「运行中重复点 A/B/C 十次仍持续发布」需要设备，代码层面只能保证状态转移不抛。

## 2. R32-02 高德对照通道被场景预设覆盖（P1）

**现象**：审查者用真实 SDK 6.4.5 跑探针的选项构建，得到
`primary.mock=false / dev.mock=false`——本该「允许模拟」的对照通道其实和主通道一模一样，对照无效。

**根因**：`AmapReader` 先 `setMockEnable(...)` 再 `setLocationPurpose(AMapLocationPurpose.Sport)`；
场景预设会把一批选项（含 `mockEnable`）重置，后设的场景把先设的开关盖掉。

**修法**：

- `location-probe/src/main/java/org/localroute/probe/AmapReader.java`
  - `baseOption()`：只放两通道共用的选项（`Hight_Accuracy`、`interval=1000`、`httpTimeOut=20000`、
    `gpsFirst` + `gpsFirstTimeout=1000`、`needAddress`、`onceLocation=false`、`sensorEnable`）
  - `buildPrimaryOption()`：**先** `setMockEnable(false)` **再** `setLocationPurpose(Sport)`，复现目标 App 的调用顺序
  - `buildDevOption()`：**先** `setLocationPurpose(Sport)`，**最后** `setMockEnable(true)`
  - 报告里两条通道分别打印最终 getter 实读值，并附一句自检结论
- `location-probe/src/main/java/org/localroute/probe/AmapOptionCheck.java`（纯 Java，不依赖 SDK）：
  `primaryOk` = `!mockEnable`、`devOk` = `mockEnable`，`describe(...)` 输出带 ✓/✗ 的一句话；
  `AmapReader.optionAssertions()` 委托给它，于是「对照失效」在报告上是**看得见的 ✗**，不会再静默。

**测试**：`location-probe/src/test/java/org/localroute/probe/AmapOptionCheckTest.java` 5 例
（主通道必须 false、对照必须 true、两者都要、describe 的 ✓/✗ 与两个数值都出现）。

**没验**：真机上高德通道是否真的收到帧——探针包需要在控制台按 `org.localroute.probe` 包名 + debug 签名登记 Key；
未登记时报告显示 `amap-sdk: UNAVAILABLE（未配置 Key）`，这是预期行为，不是代码缺陷。

## 3. R32-03 传送后出现多个发布循环（P1）

**现象**：反复点 A/B/C 后发布节奏变快/抖动（与「时快时慢」相关）。

**根因**：`scheduleNextTick()` 每次 `handler.postDelayed(tickRunnable, interval)`，传送、暂停、开始
各路径都会排一次，从不清除已排的那条 → 同一 Handler 上叠了多份 tick，发布频率翻倍。

**修法**：`simulation-core/src/main/java/org/localroute/simulation/TickScheduler.java`

- `interface Queue { boolean postDelayed(Runnable, long); void removeCallbacks(Runnable); }`
- 内部固定同一个 `guarded` Runnable（`removeCallbacks` 与 `postDelayed` 必须是同一实例才有效）
- `schedule(long)`：已有待执行 tick 时直接返回 `false`，不重复投递；`cancel()` 清状态并撤销；
  `pending()` 供诊断断言
- `SimulationService` 侧：`onCreate()` 用 `handler.postDelayed/removeCallbacks` 包出 `Queue`；
  `scheduleNextTick()` 只走 `tickScheduler.schedule(interval)`，投递失败且无待执行 tick 才
  `failAndStop(SCHEDULER_INTERRUPTED, ...)`；`cleanupEverything()` 先 `tickScheduler.cancel()`

**测试**：`simulation-core/src/test/java/org/localroute/simulation/TickSchedulerTest.java` 6 例，
含「连续排程 20 次只投递 1 次」「tick 内自我重排」「cancel 后可重排」「投递失败不留 pending」。

## 4. R32-04 Activity 进后台后悬浮条不再刷新（P1）

**现象**：把主界面切到后台，悬浮条还在屏幕上，但状态冻住——冷态点 A 之后仍显示「未运行」，按钮一直灰。

**根因**：悬浮条的状态订阅挂在 `MainActivity` 的 `snapshot().observe(this, …)` 上，Activity 一
STOPPED 观察者就停收；而 `onDestroy()` 里又会 `hide()` 掉窗口。窗口的生命周期与 Activity 不一致。

**修法**：把「悬浮会话」的所有权从 Activity 挪出来。

- `app/src/main/java/org/localroute/app/overlay/SnapshotSource.java`：`subscribe/unsubscribe` 两方法
- `OverlaySession.java`：`attach()` 已订阅时返回 `false` 不重复注册、`detach()` 未订阅返回 `false`
- `OverlayHost.java`（单例）：持 `OverlayPanel` + `LiveData<RunSnapshot>`；`subscribe` 里
  `observeForever` 并立即回放当前值，`unsubscribe` 里 `removeObserver` 并把引用置空——**成对**，
  不是「只加一个永不注销的 observeForever」；`setEnabled()` 写偏好并 attach/detach；`render()` 刷新面板
- `OverlayViewState.java`（纯 Java）：把 `RunSnapshot` 翻成 `IDLE / RUNNING_ROUTE /
  RUNNING_SINGLE_POINT / PAUSED / STARTING / TERMINAL` 与三个按钮可用性——过去只能靠真机看的东西
- `OverlayPanel.java`：`update(RunSnapshot)` 委托给 `update(OverlayViewState)`；`TERMINAL` 显示「已结束」
- `MainActivity.java`：不再持有 `overlayPanel`，改为 `overlayHost`；LiveData 观察者只渲染自己的界面；
  `onDestroy()` 不再 `hide()`（否则旋转一次屏幕窗口就没了）；`toggleOverlay()` 只调 `overlayHost.setEnabled(...)`

**测试**：`OverlayViewStateTest`（7 例：冷态两键皆灰、完成态 TERMINAL、路线/单点/暂停/启动）、
`OverlaySessionTest`（6 例：重复 attach 不重复订阅、detach 成对且停止投递、**owner 在后台仍持续收快照**、
反复开关订阅数始终 ≤1）。

**没验**：真机上「Activity 后台 → 冷态点 A → 面板立刻变成单点运行」仍需设备；代码层面已保证订阅
不依赖 Activity 生命周期。

## 5. R32-05 探针统计混算（P2）

**现象**：报告把「SDK 明确拒收的错误回调」也算进位置与距离；没有速度样本时均速显示 `0.00 m/s`，
看起来像「目标给了速度但为 0」。

**修法**：

- `simulation-core/src/main/java/org/localroute/simulation/ChannelStats.java`
  - 新增 `errorCallbacks` 与 `addErrorCallback()`；`callbacks() = 有效 + 错误`
  - 新增 `hasSpeedSamples()`、`lastArrivalNanos()`、`ageSinceLastFrameMillis(now)`（「最后回调 N 秒前」）
  - `summary()` 改为「回调 N 次（有效 X / 错误 Y）… 位移 … 米（**位置跳变累计，不是运动距离**）…
    均速 未提供（目标未给速度字段）」；零回调时显示「0 次回调（没有收到任何回调）」
- `ProbeActivity.handleAmapFrame()`：`errorCode != 0` 只 `addErrorCallback()` 并打印单帧字段，直接返回，
  **不进**距离与速度
- `ProbeActivity.showReport()`：报告头部写明「统计会话：传送测试 / 跑步路线」，加「起止时间」与各通道
  「最后回调 N 秒前」；`activity_probe.xml` 加 `checkTransfer` 复选框，勾上即按「传送测试」措辞输出
- 每次「开始监听」都 `stats.clear()`，两场测试天然分开

**测试**：`ChannelStatsTest` 新增 3 例（错误回调单独计数且位移为 0、无速度样本显示「未提供」、
`ageSinceLastFrameMillis` 跟随到达时间），并改掉旧的「0 个位置」断言。

## 6. R32-06 保存令牌只比编辑次数（P2）

**现象**：保存 A 的后台任务还在跑时切到 B（B 没被编辑过），旧回调把 B 也标成「已保存」。

**修法**：

- `app/src/main/java/org/localroute/app/ui/DraftSaveToken.java`：令牌绑 `routeId + draftGeneration + editRevision`
- `RouteEditorViewModel`：新增 `draftGeneration`，`load()` / `newDraft()` / `markDeleted()` 各 `++`；
  新增 `saveToken()` 与 `markSavedIfCurrent(token)`
- `MainActivity.doSave()`：保存前后各取/核对一次令牌，不匹配就 toast「保存期间草稿有变化，请再保存一次」

**测试**：`DraftSaveTokenTest` 8 例（匹配时清 dirty、保存中编辑仍 dirty、保存中新建草稿失效、
删除后失效、空令牌、describe、旧接口仍可用）。

  若要验证是否被当作抖动丢弃，请一次只改一个变量。」

## 9. 仍然没做的事

1. `GOGOGO_REFERENCE` 参考发布模式（`docs/13` 第 3 步）：需要 100 ms 档与「按单调时间 + 累计距离取位置」，
   会动发布链路，本轮没动。
2. 同机三方对照的正式记录与 `delivery/compatibility/zafu-2.51/<runId>/` 证据目录。
3. `DistanceDecision` 纯逻辑模块（`docs/13` 第 5 步）。
4. `SimulationService` 本身仍无自动化测试：Android 服务需要 Robolectric/仪器测试，当前工程没有这套基建，
   所以状态转换逻辑被抽成 `TaskModeSwitch`、排程抽成 `TickScheduler` 来覆盖，服务内的胶水代码仍只靠真机验证。
5. 探针高德通道需要独立登记 Key 才能真跑。
6. 卫星图 / 地点搜索、GPX 多段 `trkseg`、`hint_closed_on/off` 僵尸文案——与本次真机意见无关，仍未做。
